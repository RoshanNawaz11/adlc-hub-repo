### API Contract

**New endpoint:** `POST /runs/{thread_id}/withdraw`

**Request:**

```json
{
  "reason": "Duplicate of SO-1003"
}
```

**Response (200 OK):**

```json
{
  "status": "withdrawn",
  "reason": "Duplicate of SO-1003",
  "withdrawn_at": "2026-10-15T14:32:00Z"
}
```

**Error responses:**

- `400 Bad Request`:
  ```json
  {"error": "Reason is required and cannot be empty"}
  ```
  or
  ```json
  {"error": "Reason exceeds 500 characters"}
  ```
- `404 Not Found`:
  ```json
  {"error": "Case not found"}
  ```
- `409 Conflict`:
  ```json
  {"error": "Case is running, wait until it pauses"}
  ```
  or
  ```json
  {"error": "Case is done, cannot withdraw"}
  ```
  or
  ```json
  {"error": "Case was withdrawn on 2026-10-14T10:00:00Z: Duplicate of SO-1003"}
  ```

### Queue Message Contract (Resume Handler)

**Location:** `src/agents/queue/orders.py`, `resume_service_order` function

**Behavior change:** After loading case state, check `status` field. If `status == "withdrawn"`:

1. Skip graph invocation.
2. Write queue status to Redis:
   ```python
   key = f"order-run:{thread_id}"
   value = json.dumps({
       "status": "withdrawn",
       "reason": "<reason>",
       "withdrawn_at": "<timestamp>"
   })
   await redis.set(key, value, ex=STATUS_TTL_SECONDS)
   ```
3. Mark job as successful (no retry).
4. Log: `Case {thread_id} already withdrawn, resume ignored`.

## Risks

### Risk 1: Race condition between queue resume and withdrawal

**Scenario:** A resume job is dequeued at the same time a reviewer withdraws the case via API or CLI.

**Impact:** The resume handler may overwrite the withdrawal if both load the state before either writes back.

**Mitigation:**

- **Short-term (this ticket):** The resume handler checks the state **after loading** (see queue handler change above). If the withdrawal completed first, the resume handler sees `status == "withdrawn"` and skips work.
- **Long-term (future enhancement):** Add a `version: int` field to `State` and use optimistic locking (compare-and-swap) in both `withdrawal.py` and the resume handler. Requires investigation of `AsyncSqliteSaver`'s transaction/locking support.

**Status:** Accepted risk for initial implementation. Document in testing plan: integration test that withdraws a case, then enqueues a resume job, and verifies the resume is a no-op.

---

### Risk 2: Console notification failure is silent to the user

**Scenario:** The console backend is down when a case is withdrawn; the reviewer sees success, but the activity feed is not updated.

**Impact:** Ops must manually reconcile failed notifications from logs.

**Mitigation:**

- Best-effort semantics (per HLD AD-7): withdrawal succeeds regardless of console availability.
- Log all notification failures at `WARNING` level with `thread_id`, `timestamp`, `reason` for ops reconciliation.
- **Future enhancement:** Add a retry queue or outbox table for failed console notifications (out of scope for this ticket).

**Status:** Accepted. Monitoring/alerting on WARNING logs in `backend.py` is an ops concern, not a code change.

---

### Risk 3: Reviewer authentication not specified

**Scenario:** How is `reviewer_id` determined in API and CLI contexts?

**Impact:** Cannot populate `withdrawn_by` field without authentication context.

**Mitigation:**

- **API:** Extract `reviewer_id` from authentication token (e.g. JWT claims, session user). Requires coordination with FastAPI's auth middleware (not shown in `server.py`). If auth is not yet implemented, use a placeholder (e.g. `"unknown"` or request header `X-Reviewer-ID` for testing).
- **CLI:** Accept `--reviewer-id` argument or read from environment variable `REVIEWER_ID`. For local testing, default to `"cli-user"`.

**Status:** **Open question.** Recommend: API extracts from auth context (defer implementation detail to FastAPI team); CLI accepts `--reviewer-id` argument with a default.

2. **Reviewer authentication:** How is `reviewer_id` determined in API (auth token?) and CLI (argument? environment variable?) contexts?

3. **Console backend endpoint:** What is the exact URL and payload format for the console's activity feed notification? Is extending `report_progress` the right integration point, or should a new `report_withdrawal` function be added?

4. **CLI module location:** Should the withdrawal CLI command live in a new `src/agents/cli.py` module, be added to `run_so.py`, or exist as a standalone script (e.g. `run_withdrawal.py`)?

5. **Status key collision:** The queue resume handler writes to `status_key(thread_id)` (same key FastAPI uses for run status). Should withdrawal write a separate key (e.g. `withdrawal:{thread_id}`) or extend the existing `order-run:{thread_id}` payload with withdrawal fields?

## Testing Notes

- **State transition validation:** Unit tests for every valid/invalid transition to `withdrawn` (from `needs_input`, `needs_review`; reject from `running`, `done`, `rejected`, `failed`, `withdrawn`).
- **Reason validation:** Parameterized tests for empty, whitespace-only, exactly 500 chars, over 500 chars.
- **History recording:** Verify the history entry is appended with correct `type`, `by`, `at`, `reason` fields.
- **Persistence across restarts:** Integration test: withdraw a case, close and re-open the checkpointer, verify `status`, `withdrawn_at`, `withdrawn_by`, `withdrawal_reason` persist.
- **Queue resume no-op:** Integration test: withdraw a case, enqueue a `resume_service_order` job, verify the handler skips work and writes queue status.
- **Console notification failure:** Mock the console backend to fail (HTTP 500), verify withdrawal still succeeds and failure is logged.
- **Idempotency:** Call `withdraw_case` twice on the same case, verify the second call returns 409 Conflict with existing withdrawal details, does not modify state.
- **CLI command:** End-to-end test invoking `python -m agents.cli withdraw-case <thread_id> --reason "test"`, verify output and state changes.
- **Race condition (best-effort):** Test that enqueuing a resume job immediately after withdrawal results in a no-op (may be non-deterministic without locking; document as known limitation).
