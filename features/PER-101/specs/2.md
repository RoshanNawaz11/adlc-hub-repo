## Schema / API Contracts

### Idempotency Store Interface (from HLD AD-1)

```python
# src/agents/runtime/idempotency.py

from typing import Literal, Protocol

class IdempotencyStore(Protocol):
    async def claim(self, key: str, thread_id: str) -> Literal["claimed", "running", "completed"]:
        """
        Atomically claim the run key.
        - "claimed": This worker now owns the run. Proceed to execute.
        - "running": Another worker owns the run. Skip execution.
        - "completed": The run already finished. Skip execution.
        Raises IdempotencyUnavailable if the backend is unreachable.
        """
        ...

    async def complete(self, key: str, thread_id: str) -> None:
        """
        Mark the run as completed. Idempotent (can be called multiple times).
        Logs error if backend is unreachable, does not raise.
        """
        ...

    async def release(self, key: str, thread_id: str) -> None:
        """
        Release the claim (run paused, failed, or cancelled).
        Logs error if backend is unreachable, does not raise.
        """
        ...
```

### Redis Key-Value Schema (from HLD AD-2)

**Key:** `run-idempotency:{idempotency_key}`

**Value (running):**
```json
{
  "state": "running",
  "thread_id": "<uuid>",
  "claimed_at": "<iso8601>"
}
```

**Value (completed):**
```json
{
  "state": "completed",
  "thread_id": "<uuid>",
  "claimed_at": "<iso8601>",
  "completed_at": "<iso8601>"
}
```

**TTLs:**
- Claim (running): `IDEMPOTENCY_CLAIM_TTL_SECONDS` (default 3600)
- Completed: `IDEMPOTENCY_COMPLETED_TTL_SECONDS` (default 604800)

### `run_query` Return Schema Extension (from HLD AD-3)

Existing fields unchanged. New `reason` values:

- `"already running"`: Another worker is executing this run. **Worker must skip all status writes.**
- `"idempotent replay"`: Run already completed. Existing behavior (write `done` status) acceptable.

**Example return value when another worker owns the run:**
```python
{
    "thread_id": "...",
    "trace_id": "...",
    "skipped": True,
    "reason": "already running",
    "values": {}
}
```

**Observable outcome for resumed runs (per HLD AD-3):** When a resumed run completes, `complete` marks the store entry as `"completed"` and the worker writes `done` status to `order-run:{thread_id}`. When a resumed run pauses again, `release` deletes the store entry (allowing the run to be retried later) and the worker writes `paused` status.

## Integration Points (from HLD AD-3)

### `run_query` in `src/agents/runtime/runner.py`

**Current flow (simplified):**
```python
async def run_query(thread_id, query, service_order_id=None, resume=False):
    # 1. Build idempotency key (unchanged)
    key = idempotency_key(f"{thread_id}:{service_order_id or query}")
    
    # 2. Load snapshot
    snapshot = await checkpointer.aget(...)
    
    # 3. Paused-thread guard
    if not resume and snapshot and snapshot.next:
        raise RuntimeError("Thread paused mid-run")
    
    # 4. Old idempotency check (to be replaced)
    if not resume and already_processed(key):
        return {"thread_id": thread_id, "skipped": True, "reason": "idempotent replay", ...}
    
    # 5. Run graph
    result = await graph.ainvoke(...)
    
    # 6. Mark processed if not paused
    if not snapshot.next:
        mark_processed(key)
    
    return result
```

**New flow (changes in bold):**
```python
async def run_query(thread_id, query, service_order_id=None, resume=False):
    # 1. Build idempotency key (unchanged)
    key = idempotency_key(f"{thread_id}:{service_order_id or query}")
    
    # 2. Load snapshot
    snapshot = await checkpointer.aget(...)
    
    # 3. Paused-thread guard (unchanged)
    if not resume and snapshot and snapshot.next:
        raise RuntimeError("Thread paused mid-run")
    
    # **4. NEW: Instantiate store**
    store = get_idempotency_store()
    
    # **5. NEW: Claim (only if not resume)**
    if not resume:
        try:
            claim_result = await store.claim(key, thread_id)
        except IdempotencyUnavailable:
            raise  # Propagates to _run
        
        if claim_result == "completed":
            return {"thread_id": thread_id, "trace_id": trace_id, "skipped": True, "reason": "idempotent replay", "values": {}}
        elif claim_result == "running":
            return {"thread_id": thread_id, "trace_id": trace_id, "skipped": True, "reason": "already running", "values": {}}
        # else: claim_result == "claimed", proceed
    
    # **6. Wrap graph.ainvoke to handle cancellation**
    try:
        result = await graph.ainvoke(...)
    except asyncio.CancelledError:
        if not resume:
            await store.release(key, thread_id)
        raise
    except Exception as e:
        if not resume:
            await store.release(key, thread_id)
        raise
    
    # **7. Complete or release based on pause state**
    snapshot = await checkpointer.aget(...)  # Refresh snapshot
    if snapshot.next:
        # Paused
        if not resume:
            await store.release(key, thread_id)
    else:
        # Completed
        await store.complete(key, thread_id)
    
    return result
```

**Key decisions:**
- Claim **after** the paused-thread guard so the guard's `RuntimeError` leaves no claim behind.
- Resume flows **do not claim** (the original run already claimed). Resumed runs **do call `complete`** when they finish (marks store entry `"completed"`, worker writes `done` status).
- Resumed runs that pause again call `release` (deletes store entry, worker writes `paused` status).
- Cancellation (`asyncio.CancelledError`) must release before re-raising.
- All exceptions release before re-raising (except on resume).

### `_run` in `src/agents/queue/orders.py`

**Current flow (simplified):**
```python
async def _run(ctx, thread_id, query, service_order_id):
    # 1. Write running status
    await redis.set(f"order-run:{thread_id}", json.dumps({"status": "running", ...}))
    
    # 2. Call run_query
    try:
        result = await run_query(thread_id, query, service_order_id)
    except Exception as e:
        await redis.set(f"order-run:{thread_id}", json.dumps({"status": "failed", ...}))
        raise
    
    # 3. Write done/paused status
    if result.get("skipped"):
        status = "done"
    elif snapshot.next:
        status = "paused"
    else:
        status = "done"
    
    await redis.set(f"order-run:{thread_id}", json.dumps({"status": status, ...}))
```

**New flow (changes in bold):**
```python
async def _run(ctx, thread_id, query, service_order_id):
    # **1. Call run_query first, then decide whether to write status**
    try:
        result = await run_query(thread_id, query, service_order_id)
    except Exception as e:
        # Write failed status (unchanged, because run_query raised before returning)
        await redis.set(f"order-run:{thread_id}", json.dumps({"status": "failed", ...}))
        raise
    
    # **2. NEW: Guard against "already running"**
    if result.get("reason") == "already running":
        logger.info(f"Run {thread_id} already owned by another worker, skipping status write")
        return  # Early exit, no status write
    
    # **3. Write running status (only if we own the run)**
    await redis.set(f"order-run:{thread_id}", json.dumps({"status": "running", ...}))
    
    # 4. Write done/paused status (unchanged logic)
    if result.get("skipped"):
        status = "done"  # "idempotent replay" case
    elif snapshot.next:
        status = "paused"
    else:
        status = "done"
    
    await redis.set(f"order-run:{thread_id}", json.dumps({"status": status, ...}))
```

**Key decision:** The `"already running"` guard must happen **before** writing the `running` status. Otherwise Worker B would overwrite Worker A's status. The simplest fix is to call `run_query` first, check the reason, and exit early if `"already running"`.

**Alternative (rejected):** Move the `running` status write inside `run_query` after a successful claim. This keeps the status write and claim atomic but couples the runner to the worker's Redis contract. The guard approach is less coupled.

## Risks

### Risk 1: `run_query` Cancellation Handling Incomplete

**Impact:** If `graph.ainvoke` is cancelled but the `try/except asyncio.CancelledError` block is not added, the claim is never released. The run is blocked until the claim TTL expires (3600s).

**Mitigation:** The test suite includes a cancellation test (test case 6: `test_run_query_cancellation_releases`). The test will fail if the `release` call is missing.

**Residual risk:** Low. The test catches this before merge.

---

### Risk 2: Worker Status Write Race

**Impact:** If Worker A claims and Worker B calls `run_query` concurrently, Worker B gets `"already running"` and exits. If Worker A then crashes before writing the `running` status, the job appears stuck (no status entry exists). The claim TTL eventually expires, allowing retry.

**Mitigation:** The existing `ORDER_JOB_TIMEOUT` already bounds this. The claim TTL provides eventual recovery. This is an acceptable trade-off (prioritize correctness of the claim over status consistency).

**Residual risk:** Low. This is an existing failure mode (worker crashes are always possible). The idempotency layer does not worsen it.

---

### Risk 3: Resume Flow Calls `complete` Twice

**Impact:** A resumed run calls `complete` when it finishes. If the original run also called `complete` (before pausing), the key is written twice. This is safe because `complete` is idempotent (simple SET, not conditional), but it's wasteful.

**Mitigation:** The HLD already specifies that `complete` is idempotent. No code change needed. Document this in the `complete` method's docstring (PER-111 responsibility).

**Residual risk:** None. This is the intended behavior.

---

### Risk 4: `_run` Status Write Logic Becomes Complex

**Impact:** The status write guard introduces conditional logic (check reason, early exit). If future changes add more status write points, the guard must be applied consistently.

**Mitigation:** Keep the guard as a single early-exit check at the top of `_run`, immediately after `run_query` returns. All status writes happen after this check. Add a comment linking to the HLD AD-4 and this spec.

**Residual risk:** Low. The structure is simple (one check, one exit).
