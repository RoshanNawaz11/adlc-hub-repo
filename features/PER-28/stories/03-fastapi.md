## Overview

Implement `RunRegistry` to map client `run_id` to agent `agent_run_id` for SSE routing. Maintains in-memory mapping, provides lookup for SSE endpoint, and cleans up mapping after terminal event received. Does not track timestamps or status (agent owns all timing logic).

**CRITICAL CHANGE (per change_requests.md):** FastAPI does **not** create, decide, or delay run status. The agent owns all timing logic, including the 5-second delay. `RunRegistry` only maps IDs — no `start_time`, no `completion_time`, no `response`, no `error`, no elapsed time calculation. All status and timing lives on the agent side.

## Functional Requirements

### RunRegistry Interface

**Responsibilities:**
- Map client `run_id` to agent `agent_run_id` for SSE routing
- Provide lookup for SSE endpoint to subscribe to correct agent run
- Clean up mapping after terminal event received
- Maintain in-memory mapping only (no timestamps, no status)

**Operations:**

#### Registration

**Inputs:**
- `run_id`: Client-facing UUID4 identifier (generated by POST /query endpoint)
- `agent_run_id`: Agent service's internal run identifier (from agent's immediate reply)

**Outputs:**
- Success: Mapping stored
- On collision: Error (run_id already exists)

**Behavior:**
- Stores `run_id → agent_run_id` mapping
- Validates run_id uniqueness (collision detection)
- No timestamp recording
- No status tracking

---

#### Lookup

**Inputs:**
- `run_id`: Client-facing UUID4 identifier

**Outputs:**
- On success: `agent_run_id` string
- On missing: Error (run_id not found)

**Behavior:**
- Returns stored `agent_run_id` for given `run_id`
- Raises error if run_id not found (SSE endpoint returns 404)
- No status or timing information returned

---

#### Cleanup

**Inputs:**
- `run_id`: Client-facing UUID4 identifier

**Outputs:**
- Success: Mapping removed
- On missing: Error (run_id not found)

**Behavior:**
- Removes `run_id → agent_run_id` mapping
- Called after terminal event forwarded (in `finally` block)
- No periodic cleanup needed (no timestamps to leak)

---

### Error Handling Strategy

**Collision (duplicate run_id):**
- Should never occur (UUID4 collision probability negligible)
- If occurs: reject registration with descriptive error
- Allows detection of logic errors (e.g., run_id reuse bug)

**Missing run_id:**
- Lookup/cleanup of non-existent run_id raises error
- Caller (Story 5 SSE endpoint) catches and returns 404
- Prevents silent failures

## Open Questions

1. **Persistence requirement:** Current design is in-memory only. If backend restarts, all run mappings are lost. Acceptable for MVP, or should we add persistence (e.g., Redis)? Affects horizontal scaling.

2. **Concurrency model:** If backend deploys multiple worker processes, each process has its own registry instance. Run mappings are not shared across workers. Should we use a shared backend (Redis), or route requests by `run_id` (sticky sessions)?

3. **Monitoring/metrics:** Should registry expose metrics (e.g., active run count)? Useful for memory leak detection and capacity planning.

4. **Stack confirmation:** Current repo-tree shows "(repo path not mapped; do not invent a stack)". Before implementing, confirm:
   - Language and framework

## Risks

### Risk 1: Memory leak if cleanup skipped
**Impact:** Registry grows unbounded, eventual OOM  
**Likelihood:** Low (simpler than old design — only IDs stored, cleanup in `finally` block)  
**Mitigation:** Cleanup called in `finally` block of SSE endpoint (Story 5). No periodic cleanup needed (no timestamps to leak).

### Risk 2: KeyError on missing run_id
**Impact:** SSE endpoint crashes if run_id not found  
**Likelihood:** Medium (race condition: POST /query fails but client connects to SSE)  
**Mitigation:** Story 5 SSE endpoint catches error, returns 404.

### Risk 3: No horizontal scaling
**Impact:** Can't distribute load across multiple backend processes  
**Likelihood:** High for production  
**Mitigation:** Current design sufficient for MVP. For production, migrate to Redis-backed registry (same interface, different backend).

### Risk 4: No persistence across restarts
**Impact:** Active run mappings lost if backend restarts  
**Likelihood:** Low in containerized environments (orchestrator handles restarts gracefully)  
**Mitigation:** Document limitation. If persistence required, add Redis backend.

### Risk 5: Stack-specific concurrency issues
**Impact:** Thread-unsafe operations in multi-threaded environments  
**Likelihood:** Depends on stack (low for async/event-loop, medium for multi-threaded)  
**Mitigation:** Implementation adds locking if needed (e.g., `threading.Lock` in Python multi-threaded mode). Current design assumes single-threaded async (FastAPI/asyncio, Node.js/event loop).

## Notes

- **Singleton pattern:** Registry instantiated once at app startup and passed to endpoints via dependency injection. Story 4 handles DI setup.
- **No timing logic:** Deliberate design choice per change_requests.md. All timing, status generation, and delay logic lives on the agent side.
- **Cleanup timing:** No periodic cleanup task needed. Cleanup happens immediately after terminal event in SSE endpoint's `finally` block (Story 5).
- **Error messages:** Use descriptive messages in errors for easier debugging (e.g., "run_id {run_id} already exists").
- **Pure pass-through:** This component's simplicity is the point. It does one thing: map client `run_id` to agent `agent_run_id`. No lifecycle tracking, no state machine, no timing authority.
- **Implementation deferred:** Concrete file paths, imports, and language-specific syntax removed per ADLC rule: "File paths and stack MUST match repo context / existing tree. Never invent another language or framework." Implementation awaits repo-tree mapping.
- **Stack-agnostic design:** Operations defined as behavioral contracts, not language-specific code. Implementation adapts to repo's actual stack.
